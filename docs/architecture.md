# Архитектура git-autoc

## 1. Суть инструмента

`git-autoc` — CLI, который генерирует conventional commit message для
застейдженных изменений с помощью LLM.

Инструмент — это конвейер из пяти шагов:

```
CLI → контекст → промпт → модель → результат/коммит
```

Принцип: данные текут в одну сторону. Каждая ступень не знает, что происходит
дальше и откуда пришли данные. Путь данных читается сверху вниз.

## 2. Структура проекта

```
src/git_autoc/
  cli.py
  pipeline.py
  context.py
  prompt/
    engine.py
    loader.py
  config/
    settings.py
    store.py
  integrations/
    git.py
    llm.py
```

| Модуль            | Обязанность                                            |
|-------------------|--------------------------------------------------------|
| `cli.py`          | Ввод/вывод пользователя                                |
| `pipeline.py`     | Оркестрация: порядок действий                          |
| `context.py`      | Соответствие «имя блока → источник данных»             |
| `prompt/engine.py`| Парсер и рендерер шаблонов промптов                    |
| `prompt/loader.py`| Чтение файлов шаблонов                                 |
| `config/settings.py`| Модель конфигурации                                  |
| `config/store.py` | Чтение/запись конфиг-файла                             |
| `integrations/git.py` | Команды git                                        |
| `integrations/llm.py` | Вызов модели через OpenAI-compatible API            |

## 3. Модули

### cli.py

**Обязанность:** единственное место, где пользователь взаимодействует с
инструментом.

Живёт здесь:
- typer-команды и флаги;
- интерактивные вопросы («Stage all?», «Коммитим? y/N/e»);
- вывод результата и ошибок.

Не живёт здесь:
- логика генерации, работы с git, LLM или файлами.

cli — тонкая прослойка: вызывает `pipeline` и форматирует то, что тот вернул.
Интерактивность принадлежит cli, потому что это UI: `pipeline` не спрашивает
пользователя, он возвращает данные, а cli решает, что показать и о чём спросить.

### pipeline.py

**Обязанность:** описать последовательность действий («рецепт»).

`pipeline` связывает все модули в правильном порядке:

1. прочитать шаблон промпта (через `prompt/loader`);
2. узнать у `prompt/engine`, какие блоки шаблон требует;
3. для каждого блока достать данные через `context`;
4. отдать данные в `prompt/engine` на рендер;
5. вызвать модель через `integrations/llm`;
6. вернуть результат в cli (и выполнить коммит, если cli попросил).

`pipeline` не знает, *как* git выполняет команды, *как* модель отвечает и *как*
выглядят файлы — он знает только порядок действий. Это делает его читаемым как
инструкцию.

### context.py

**Обязанность:** соответствие «имя блока → источник данных».

Это простой словарь: имя → функция.

```python
# context.py
def _commits(param):  return git.get_recent_commits(int(param))
def _diff(_):         return git.get_staged_diff()
def _branch(_):       return git.get_current_branch()

CONTEXT = {
    "commits": _commits,
    "diff":    _diff,
    "branch":  _branch,
}
```

`pipeline` делает одну строку: `context.CONTEXT[name](param)`.

`context` — единственное место, где известно «что откуда берётся». Новый блок =
одна функция + одна запись в словаре — ни `pipeline`, ни `prompt`, ни `git`
менять не нужно. Блок из не-гитового источника (конфиг, окружение, файл) — такая
же функция в этом же словаре.

Контекст ленивый: если в шаблоне нет `{commits:5}`, соответствующая функция не
вызывается.

### prompt/engine.py

**Обязанность:** парсер и рендерер шаблонов.

- парсит шаблон, находит `{name:param}`;
- возвращает список требуемых блоков (чтобы `pipeline` знал, что доставать);
- подставляет значения блоков в шаблон и возвращает готовый промпт.

`engine` — чистая логика, без I/O: не читает файлы (это `loader`), не знает,
откуда берутся данные блоков (это `context`). Он знает только синтаксис блоков,
поэтому тестируется без git, LLM и файловой системы.

### prompt/loader.py

**Обязанность:** чтение файлов шаблонов.

Превращает файл шаблона в объект `Template`. Ничего, кроме работы с файлами,
не делает. Зависит от `engine` (использует его тип `Template`).

### config/settings.py

**Обязанность:** модель конфигурации.

Поле модели `Settings`: настройки, дефолты, валидация, правила обязательности.
Чистая логика, без I/O — файлы не читает и не пишет (это `store`).

### config/store.py

**Обязанность:** чтение/запись конфиг-файла.

Превращает TOML-файл в объект `Settings` и обратно; создаёт дефолтный конфиг,
если его нет. Зависит от `settings` (использует его тип `Settings`).

### integrations/git.py

**Обязанность:** команды git.

Тонкие обёртки над subprocess:
- чтение: staged diff, список застейдженных файлов, последние коммиты, текущая
  ветка, наличие staged/unstaged изменений;
- действия: `stage_all`, `commit`, `commit_edit`.

Правила: возвращать простые типы (`str`, `list[str]`, `bool`), бросать понятные
типизированные ошибки, не знать ничего о промптах, конфиге или LLM.

### integrations/llm.py

**Обязанность:** вызов модели.

Клиент OpenAI-compatible API, конфигурация вызова (base_url, model, api_key,
temperature, max_tokens), перевод ошибок API в типизированные ошибки проекта.

Принимает готовые сообщения и настройки, возвращает строку. Не строит промпты
(это `prompt`), не знает про git и файлы.

## 4. Зависимости

```
cli → pipeline → prompt, config, context, integrations
context → integrations
prompt/loader → prompt/engine
config/store → config/settings
```

- `cli` зависит только от `pipeline`.
- `pipeline` зависит от всех модулей.
- `context` зависит от источников, которые маппит (сейчас — `git`).
- `loader`/`store` зависят только от своих контрактов.
- `engine` и `settings` ни от чего не зависят — чистая логика.
- `git` и `llm` ни от чего не зависят — самодостаточные адаптеры.

Петель нет. Любой модуль можно читать, не держа в голове остальные.

## 5. Поток данных на примере

Сценарий: пользователь запускает `autoc` в репозитории с застейдженными
изменениями.

1. **cli**: парсит флаги, вызывает `pipeline`.
2. **pipeline**: просит `prompt/loader` прочитать шаблон по умолчанию.
3. **pipeline**: отдаёт шаблон в `prompt/engine.parse`, получает список требуемых
   блоков.
4. **pipeline**: для каждого блока зовёт `context.CONTEXT[name](param)` — например
   `context.CONTEXT["commits"]("5")` для `{commits:5}`, а тот вызывает git.
5. **pipeline**: отдаёт шаблон + значения в `prompt/engine.render`, получает
   готовые сообщения.
6. **pipeline**: зовёт `integrations/llm.generate(messages)`.
7. **pipeline**: возвращает сообщение в cli.
8. **cli**: показывает результат, спрашивает «Коммитим?», при согласии вызывает
   `pipeline.commit(...)`.

Шаг 4 ленивый: если в шаблоне нет `{commits:5}`, git не вызывается.

## 6. Кастомные промпты

Промпт — это данные, а не код. Пользователь задаёт свой шаблон в файле шаблона,
а инструмент подставляет в него информационные блоки:

```
... last 5 commits: {commits:5}
```

Синтаксис блока: `{имя:параметр}`. Имя — какой блок взять, параметр — настройка
блока (например, количество коммитов).

Список допустимых имён и параметров описывает `prompt` (синтаксис), а
соответствие «имя → источник данных» — `context`. Планируются блоки `commits`,
`diff`, `files`, `branch` и расширение в будущем.

Именно поэтому промпт живёт в файлах, а не зашит в код: он становится входными
данными конвейера.

## 7. Обработка ошибок

Один понятный маршрут:

```
модуль бросает типизированную ошибку → pipeline пропускает/оборачивает → cli форматирует
```

- Модули бросают типизированные ошибки проекта.
- `pipeline` не глушит ошибки: либо пропускает, либо оборачивает в более
  осмысленную для пользователя.
- `cli` ловит ошибки на верхнем уровне, выводит в понятном виде и завершает
  процесс с ненулевым кодом.

В `cli` нет обработки ошибок каждого модуля по отдельности — только общий
форматтер.

## 8. Тестирование

Чистые модули — самые дешёвые тесты, адаптеры — самые хрупкие:

- **`prompt/engine` и `config/settings`** — напрямую, без моков (чистая логика).
- **`pipeline`** — с фейковыми зависимостями (передать фейк как параметр).
- **`context`** — с фейковым `git`.
- **`git`, `llm`, `store`, `loader`** — минимально, только ключевые пути и ошибки.
- **`cli`** — интеграционные тесты через typer CliRunner с фейковым `pipeline`.

## 9. Правила на будущее

- Данные текут в одну сторону; модули не знают о том, что происходит дальше.
- Новый блок данных = функция + запись в `context` + описание в `prompt`.
- Новая настройка = поле в `settings` + ключ в `store`.
- Новая интеграция = модуль в `integrations/`.
- Интерактивность — только в `cli`.
- Никакого глобального состояния: зависимости передаются явно.
